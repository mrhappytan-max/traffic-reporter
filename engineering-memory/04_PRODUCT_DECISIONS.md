# PRODUCT_DECISIONS.md — traffic-reporter (路況播報員)

Deliberate product/architecture decisions and the reasoning behind them — not a change log (see `PROJECT_HANDOFF.md` for round-by-round history) and not a current-state snapshot (see `ENGINEERING_STATUS.md`). Read this when a decision below looks "wrong" before changing it — it was very likely made on purpose, for a specific reason recorded here.

---

## V1.8.6.7 — 24h Pipeline Trace + 查修頁

### Why a second debug log instead of extending `broadcastProvenance.js`

`broadcastProvenance.js` was deliberately scoped, from V1.8.6.4 onward, to "only a genuinely-sent LINE message" — that scope is what makes it cheap (few writes/day) and safe to keep at 48h TTL. Widening it to cover every rejected/deduped/suppressed/gated event as well would have changed its write volume by an order of magnitude and made its 48h TTL a real storage question, all for a fundamentally different question ("what happened to this event" vs. "why did that sent message look like that"). Two purpose-built logs, each cheap for its own scope, beat one log doing two jobs at two different costs. Neither re-implements the other's classification/eligibility/KM-resolution logic — see `PROJECT_HANDOFF.md` §23's comparison table.

### Why 24h TTL, not 48h like provenance

Directly follows from the scope decision above: Pipeline Trace's write volume (every Hsinchu-filtered event this run, not just successful pushes) is meaningfully higher than provenance's. A shorter TTL keeps total stored volume bounded by `events/tick × ticks/day` regardless of retention length, without needing a separate storage-growth mitigation. 24 hours also matches the actual use case this feature was built for — "查修" a specific recent incident, not build a historical archive (that's what `RELEASE_SUMMARY_*.md`/git history are for).

### Why accumulate in memory and write once, not once per pipeline stage

The task's own instruction ("每一筆事件只寫一次 KV，不要每個 stage 各寫一次") matches this project's existing "儘量少量 KV 操作" discipline (see e.g. `dedupe.js`'s own module comment: "writes only happen when something actually needs to change"). A per-stage write would multiply KV operations by the number of stages an event passes through for no additional information — the SAME final record is producible from one write at the end, and a partial multi-write record would also leave a genuinely ambiguous state on a mid-run crash (which stages actually got recorded?). One record, one write, at the one point an event's lifecycle for this run is actually over.

### Why the trace page has zero client-side JavaScript

The existing Admin CSP (`security/adminAuth.js`'s `applyAdminSecurityHeaders`, `default-src 'none'`, no `script-src` exception) was already a deliberate V1.6.3-era decision — "this project ships no external JS/CSS on any admin page." Extending that CSP just for this one page would have been the first exception to a rule that's held for every other admin page so far, for a feature (expand/collapse, GET-query filters) that native HTML (`<details>/<summary>`, a plain `<form method="get">`) already provides without any script at all. Keeping the CSP unchanged also keeps the Worker's own complexity/resource footprint down, per the task's own explicit instruction ("不要做花俏 Dashboard framework... 維持 Worker 簡單、快速、低資源").

### Why upstream/normalized fields are captured at normalize time, not re-derived at trace-build time

Same principle already established for `event.provenance` (V1.8.6.4) and `event.nonCollisionAnomalyDetail` (V1.8.6.6): a raw field's value is captured ONCE, where it's already in scope during normalization, as a debug-only field on the event object — never re-parsed from a stored raw payload (which this project's privacy boundary forbids storing at all) and never re-derived by a second, potentially-drifting piece of logic. This is also what makes "0 additional upstream calls" true by construction rather than by discipline: there is no code path in `pipelineTrace.js` that could reach for a raw TDX/PBS field it wasn't already handed.

## Branch integration (`integration/v57.2-v1.8.6.5-production`) — why full reconciliation, not "pick the newer branch"

### Why merge both lineages instead of just redeploying whichever branch is "more complete"

Neither branch was disposable: the V57.2 branch was carrying Production's actual live traffic (Shared Traffic Feed consumed by another project, its CCTV top-up, TDX-gated freeway broadcast — real, currently-relied-upon behavior), while `main` carried genuinely completed, reviewed work (V1.8.6.4 provenance, V1.8.6.5 KM Location Resolver) that had simply never reached users. Discarding either side to "just ship the other one" would either regress a live consumer-facing contract or throw away completed, already-reviewed work — both are real costs, not a close call. A real 3-way merge, with every conflict resolved by tracing actual call paths rather than `ours`/`theirs`, was the only option that loses nothing on either side.

### Why the V1.8.6.6 fix was verified empirically before being pulled in, not merged on assumption

The task explicitly asked whether the reclassification fix was still needed after the main+V57.2 merge, or whether integration alone might already handle it. Rather than guessing either way, the actual raw-record shape from the real incident was run through the merged classifier first — it still misclassified `EventSubType:'其他異常告警－行人誤闖'` as `accident`, confirming the fix was genuinely still required, not a leftover from a state the merge had already superseded. This is the same "不要猜" discipline applied to a merge decision, not just to data.

### Why the branch-split root cause is documented as a process gap, not just patched away

Merging the two lineages fixes THIS instance of the split, but the underlying cause — a lineage branch created for isolated work, never merged back, silently becoming Production's actual deploy source while `main` moved on independently — could recur with any future long-lived feature branch. Recording it here (and in `ENGINEERING_STATUS.md`'s branch-split section) as an explicit "verify which branch Cloudflare actually deploys from, don't assume `main`" is a deliberate decision to treat this as a standing verification step, not a one-time cleanup.

## V1.8.6.5 — KM Location Resolver

### Why an offline, imported official dataset — not a runtime Google/TDX lookup

A runtime geocoding call (Google Maps Geocoding API, or re-querying TDX for richer location data) would add: a paid API dependency, a new network round-trip on the Cron hot path (risking the same "CCTV took too long, whole tick delayed" class of bug V1.8.5 already fixed once), a new failure mode with no offline fallback, and a new external cost surface with no budget precedent (TDX's own usage is already metered and reconciled — see `PROJECT_HANDOFF.md` §18). An offline, pre-imported official dataset costs exactly one thing: Worker bundle size (see `ENGINEERING_STATUS.md`'s watch item) — a known, measurable, zero-runtime-risk, zero-recurring-cost trade, and it matches this project's existing "zero extra TDX/PBS calls" discipline instead of adding a new one for Google.

### Why WGS84 for the provincial dataset specifically

Dataset 7040 publishes coordinates in both WGS84 (`lon_wgs84`/`lat_wgs84`) and TWD97 TM2 (`twd97_x`/`twd97_y`). WGS84 is what Google Maps' own URL format expects (`?query=<lat>,<lng>`) — using it directly means zero coordinate reprojection code, zero chance of introducing a projection-conversion bug. The dataset's own QA notes (`data/road-location/archive/README_RAW_CONTRACT.md`) additionally flag that a small number of rows carry an inconsistent or wrong-zone TWD97 pair, while "the WGS84 columns are correct in every case" — so WGS84 is also the objectively more reliable column, independent of the format-matching argument.

### Why left/right sign-pair mileposts are deduplicated (10m bucketing)

Dataset 7040 publishes a LEFT and a RIGHT physical sign for most markers, ~1m apart, as two separate rows (`install_position` 左側/右側) — a real, correct feature of the source data, not noise, but redundant for this resolver's purpose (a driver doesn't care which side of the road the physical sign is bolted to; the resolver's own `PROVINCIAL_TOLERANCE_KM` is 0.6km, three orders of magnitude coarser than the ~1m gap). Deduplicating to one point per 10m bucket (preferring a single 中央 sign when one exists) roughly halves the generated dataset (30,079 → 22,563) with zero loss of resolvable precision, and does not touch the raw file itself — this is purely the importer's own "compact" step, its explicitly documented job.

### Why provincial location = county/township/village, never a guessed street address

Dataset 7040 provides `county`/`township`/`village` per point — real, verifiable administrative units — but no street/house-number field. Composing a plausible-looking street address from KM + road name alone would require guessing, which this project's standing "不要猜" rule forbids everywhere else (see e.g. `PROJECT_HANDOFF.md` §20's provenance-audit section on never fabricating a location). county+township+village is exactly as precise as the OFFICIAL data supports and not one bit more — a driver gets "苗栗縣造橋鄉造橋村", not an invented "造橋鄉中正路123號" that might be wrong by kilometers.

### Why freeway sections are described by bracketing interchange/service-area, not a raw KM range

A KM number alone means nothing to most drivers; a named interchange or service area is how Taiwanese freeway signage and radio traffic reports already describe location, and it's exactly what datasets 166496/8161 provide. Two real facility names bracketing the event's KM ("湖口服務區－竹北交流道路段") communicate "roughly here, between these two landmarks" without implying false precision the 100m-milestone dataset alone could give but a driver couldn't act on. This mirrors — and, once real data landed, supersedes with more accurate names — the pre-existing hand-curated 國1/國3-only anchor table in `roadSectionLabel.js` (§14-era), which was always acknowledged as a stopgap pending real official data.

### Why Google Maps gets a bare `?query=` URL, never the Maps API

`https://maps.google.com/?q=<lat>,<lng>` (short form since the V1.8.6.5 UI hotfix; originally `?api=1&query=`, functionally equivalent) requires no API key, no billing account, no request quota, and no new secret to manage — it's a public, stable, documented URL format that opens the exact coordinate in any client (app or browser) the recipient already has. Calling the actual Google Maps API (Geocoding, Places, Static Maps, or a URL-shortener API) would add a paid external dependency and a new runtime network call for something a plain URL already does for free, with zero added value for this project's use case (a LINE message needs a tappable link, not an embedded image or a resolved address string — the resolver already produces the address string itself, from official data).

## V1.8.6.8 — Driver-Relevant Event Broadcast Time Policy

### Why eventActive and broadcastWindowActive are kept as two separate axes, not merged into one flag

They answer genuinely different questions: eventActive is a fact about the WORLD (is the official announcement's own window covering right now), broadcastWindowActive is a fact about THIS PRODUCT (is it currently within the hours this Worker chooses to interrupt a driver at all). Collapsing them into one boolean would make it impossible to ever again distinguish "this construction notice's own window hasn't started yet" from "it's 11pm and we just don't push routine notices right now" — which is precisely the diagnostic gap section 4 of this round's task was written to close. Keeping them separate, visible fields in Pipeline Trace costs nothing (both were already being computed, just not exposed) and directly serves the "an administrator should never need to read code to know why" goal.

### Why the 60-minute forecast leniency was deliberately left untouched

An early reading of this round's own task language ("eventActive = true AND broadcastWindowActive = true AND 原有 relevance 條件成立") could be taken to imply removing the pre-existing forecast pre-announcement (`isBroadcastRelevant`'s "starts within 60 minutes" allowance) for scheduled/announced events, since requiring `eventActive` as an ADDITIONAL AND-condition on top of `relevance` would make the forecast-only case (not yet started, but within 60 minutes) newly rejected. This was NOT implemented: there is an existing, deliberately-authored, currently-passing test (`broadcastPipeline.test.js`'s "forecast event crossing into the 60-minute window is pushed once...") explicitly asserting this behavior for a `type:'construction'` event, and the task's own required test list (section 8) never exercises the forecast boundary at all — every worked example and required test either checks well after an event has started or well after it has ended. Changing product behavior on an ambiguous reading, when the explicit constraints ("不要改壞既有架構", "不要猜") point the other way, is exactly the kind of unrequested behavior change this project's standing discipline forbids. `eventActive`/`eventTimeStatus` were built as new, additive DIAGNOSTIC fields; `isBroadcastRelevant`'s actual broadcast decision is unchanged.

### Why the cross-midnight fix is unconditional arithmetic, not keyed on a "翌日"/"次日" marker

A schedule whose end hour is numerically less than or equal to its start hour (e.g. 21 to 6) can only sensibly mean "the following calendar day" — there is no plausible reading where "21時至6時" means the end happened 15 hours before the start. Requiring the source text to also say "翌日"/"次日" before applying this correction would leave the bug in place for any real announcement that expresses the same fact without that exact marker (e.g. relying on 24-hour-style hour numbers, or phrasing this project has not seen yet) — "不要猜" cuts against assuming upstream will always use one specific marker word, not against making a determinate arithmetic correction. The marker, when present, is still recognized (for regex disambiguation and readability) — it's just not load-bearing for the rollover decision itself.

### Why the recurring-daily/multi-day-range parser resolves fresh on every call instead of representing a stored recurring schedule

`computeEffectiveWindow` (and everything under it) has always been a pure, stateless, called-fresh-every-Cron-tick function — there is no existing concept of a stored/cached schedule anywhere in this pipeline, and introducing one just for this feature would be a second, competing way of representing "when is this event relevant," exactly what section 7 of this round's task forbids. Resolving the ONE relevant concrete occurrence (active-now, or nearest-future, or most-recent-past) relative to `referenceDate` on every call keeps the exact same calling convention every other consumer of `computeEffectiveWindow` already relies on, at the cost of a few extra date comparisons per call — a cost that is already amortized by this whole layer being pure and cheap.

### Why the direction-equivalence table was extracted to its own module instead of pipelineTrace.js importing it from pbs/normalize.js directly

`pbs/normalize.js` already imports `buildUpstreamSnapshot` FROM `pipelineTrace.js` (V1.8.6.7) — a `pipelineTrace.js -> pbs/normalize.js` import would have created a circular dependency. Rather than duplicate the table (which this project's own standing rule explicitly forbids — "不要複製相同規則到多個 formatter/classifier"), it was moved to a small, dependency-free module (`directionEquivalence.js`) that both files import from, with `pbs/normalize.js` re-exporting the same name unchanged so no other importer (including its own internal use, and the existing `test/pbsNormalize.test.js`) needed to change at all.

## V1.8.6.9 — Mobile-first Deployment Guard

### Why a build-time-generated file instead of `wrangler.jsonc` vars or a runtime API call

Three options exist for a Worker to know its own deployed commit: (1) hardcode it in `wrangler.jsonc`'s `vars` — rejected outright, the task explicitly forbids hardcoding a single commit, and it would need a code change (and therefore a NEW commit, invalidating itself) on literally every deploy; (2) call the GitHub or Cloudflare API at runtime — rejected, the task explicitly forbids this, and it would add a real external dependency (latency, failure mode, rate limit) to a value that never actually changes between requests within one deploy's lifetime; (3) capture it once, at build time, into a plain bundled JS module — the only option that is both zero-runtime-cost and genuinely fresh every deploy, since the build step runs on the exact commit being deployed. `scripts/generateBuildMetadata.mjs` doing this via `git` commands (rather than requiring a specific Cloudflare-provided CI variable this repo cannot independently confirm exists) also makes the mechanism portable to any git-based CI, not coupled to one platform's unverified environment contract.

### Why `expectedMainCommit` is captured at build time, not compared against a live GitHub call

The task is explicit: "不要在 runtime 為了比對版本額外呼叫 GitHub." The apparent tension — "how can build time know what main's CURRENT head is" — resolves because a build triggered BY a push to main is, definitionally, building a commit that IS (at that moment) main's head; `git rev-parse origin/main` in that same checkout is a same-build-time, zero-network confirmation of that fact, not a live external check. When that ref genuinely can't be resolved (a shallow/detached checkout with no remote-tracking ref), the code refuses to fabricate a comparison — it falls back to "assumed same as deployed" and labels the source honestly, so the drift check can never manufacture a false mismatch from a value it never actually verified.

### Why `/version` exists as a SEPARATE, unauthenticated endpoint instead of just relaxing `/admin/deployment-status`'s auth

Loosening Admin Auth for one path, even a "harmless-looking" one, would have meant the SAME `requireAdminAuth` gate no longer uniformly protects everything in `ADMIN_PATHS` — a maintenance trap where a future change to that Set could accidentally inherit the relaxed behavior. A separate, deliberately tiny public endpoint with its own explicit, auditable field whitelist (5 fields, enforced by a dedicated test asserting `Object.keys()` exactly) keeps the Admin Auth boundary absolute (every single `ADMIN_PATHS` entry, no exceptions, no least-privileged carve-outs to remember) while still solving the actual problem: an automated verifier needs SOME way to confirm the deployed commit without a password it may not have.

### Why deployment drift stays out of `/health`'s severity computation this round

The task explicitly allowed folding drift into `/health`'s status tier ("可以把 deployment drift 顯示成 degraded/critical") but conditioned it on first checking the existing severity contract ("請先檢查目前 health severity contract，不要破壞既有健康邏輯"). That check found real, wide coupling: dozens of existing tests call `handleHealth(env)` with no way to inject a "known-good deployment" state, and this dev/test environment's own checked-in placeholder metadata always reads as drifted by design (an un-generated build IS a legitimate drift signal — see test scenario 4). Nudging severity from that would have flipped essentially every existing `'normal'`-tier assertion in `test/health.test.js` for a fact unrelated to what those tests actually verify (TDX/PBS/LINE/KV health). A separate, clearly-labeled display card satisfies the task's actual goal — a person glancing at `/health` sees version drift immediately — without touching a severity contract that many other tests already depend on meaning exactly one thing.

### Why the proxy-denial detection checks a specific header, not the status code alone

A generic "treat any non-2xx as blocked" rule would silently swallow a genuine application-level failure (e.g. the Worker itself returning 500, or `/version` genuinely gone missing after a bad deploy) as if it were merely a sandbox network restriction — exactly the kind of false negative that would make `verify-production-deploy.mjs` useless for its actual job. Conversely, treating this environment's specific proxy-denial 403 as a hard FAIL would make the verifier permanently unable to report anything but failure from a sandbox with this exact egress policy, contradicting the task's explicit "不要因網路被擋就把整個部署視為失敗." Checking for the proxy's own unambiguous, documented signal (`x-deny-reason` response header, confirmed via `$HTTPS_PROXY/__agentproxy/status`) rather than the numeric status code alone lets the script tell these two situations apart correctly, instead of guessing.

## V1.8.6.9a — Pipeline Trace Mobile UX / Taiwan Time / Dark Mode

### Why the fix was scoped to a new `formatTaipeiHHMM()`, not a broader time-handling refactor

The bug was NOT that this page lacked correct Taiwan-time logic — `formatTaipeiInstant`/`taipeiParts` (§24/V1.8.6.8) already existed and were already correct, already used elsewhere on the same page. The bug was that exactly one display spot (the per-row summary column) had its own separate, never-migrated `toISOString().slice(11,16)` computation that nobody had gone back to fix when the correct helper was introduced. The right-sized fix is to make that ONE spot use the SAME already-correct helper, not to re-derive Taiwan-time handling from scratch or touch any of the (already correct) call sites elsewhere on the page — a broader refactor would touch code that was never broken and risk introducing a new inconsistency in the process of "fixing" one that no longer needs fixing.

### Why the filter `<select>` options are built from `SOURCE_LABELS`/`STATUS_META` instead of a new constant list

Both objects already exist in this exact file and are already the single source of truth for what a row's own badges display — reusing them via `Object.entries()` for the dropdown means the two can never drift apart (a hand-typed second list of "the eight status values" would silently go stale the next time a status is added to `STATUS_META`, e.g. `pipelineTrace.js`'s `computeStatus` gaining a new outcome, and nobody remembers to also update a second list nobody's looking at). This is the same "不要複製相同規則到多個地方" principle already applied earlier in this project (see `directionEquivalence.js`'s extraction in V1.8.6.8) — one object, two consumers (row rendering, filter rendering), not two objects that happen to agree today.

### Why dark mode has no toggle / `prefers-color-scheme` media query — it's unconditionally dark

The task's own instruction was "/admin/pipeline-trace-view 改為深色介面" — an instruction to change what the page IS, not to offer the viewer a choice between two versions of it. This is a single-operator admin diagnostic page reached deliberately (Basic-Auth-gated, not something a casual visitor lands on), not a public page where respecting a visitor's OS-level light/dark preference matters for a broad, unknown audience. Adding a `prefers-color-scheme` branch would double the CSS surface (and therefore the number of places a future edit could introduce a light/dark inconsistency) to solve a preference nobody asked to be respected — the reported problem was specifically "白底太亮,手機夜間查看不舒服," not "let me choose." `color-scheme: dark` is set unconditionally for exactly this reason: it's a statement of fact about this page, not a hint about the user's own system setting.

### Why `road`/`rawId` stayed `<input>` while `source`/`status` became `<select>`

The distinguishing test is whether the field's value space is closed and already enumerated somewhere in this code (source/status: yes, both are the same finite key sets already rendered on every row) versus genuinely open-ended (road: any road name substring an administrator might type; rawId: an upstream-assigned identifier with no fixed format this project controls). Converting road/rawId to a dropdown would require this page to first enumerate every road name/rawId ever seen — a new, unrequested feature (and a KV scan cost) the task never asked for, to solve a problem (validation friction) that only exists for the genuinely closed fields.

## V1.8.7.0 — Dynamic Shoulder Broadcast + Single-CCTV Strategy

### Why dynamic-shoulder classification never changes `event.type`

The obvious alternative — adding a new `type: 'dynamic-shoulder'` — would have meant re-deriving eligibility, dedupe.js's fingerprint field set, CCTV eligibility's own type check, and every existing test that enumerates the closed set of `type` values, all to represent a fact this project already had a cheaper, additive way to express: `event.dynamicShoulder` being present IS the fact "this is a dynamic-shoulder event," and every consumer that cares (messageFormat.js, dynamicCollage.js, dedupe.js, notified.js) can branch on its presence directly. Leaving `type:'control'` alone means `broadcastRules.js`'s existing `ALWAYS_ELIGIBLE_TYPES` already covers it with zero changes, and — critically — every OTHER control-typed event (a lane closure, a routine 車道管制) keeps its exact pre-existing behavior automatically, by construction, rather than by remembering to exclude a new type value from every place that previously assumed `type` was one of the original six/seven.

### Why classification checks text evidence across four fields instead of trusting whichever TDX field happens to be present first

`tdx/normalize.js`'s own `mapRoadEventType` already establishes the pattern this reuses: TDX's real records put a broad category in one field and a more specific signal in another, and stopping at the first present field risks discarding the more specific one. For dynamic-shoulder specifically, the real Production fixture's EventType/EventSubType are bare numeric codes (`4`/`498`) that carry no independently-confirmed meaning in this codebase — TDX's live documentation is unreachable from this sandbox to verify what they mean, and guessing "498 always means dynamic shoulder" is exactly the kind of assumption a future TDX schema change (or code reuse) could silently break. Scanning all four candidate fields for the actual Chinese-text evidence, rather than trusting a numeric code, means the classifier keeps working correctly even if TDX's numbering scheme changes, and fails closed (no classification) rather than mis-classifying when the code doesn't match anything expected.

### Why OPEN/STOPPED is expressed as an addition to the EXISTING fingerprints, not a new state-tracking mechanism

This project already has exactly the right primitive for "did the driver-relevant content of this event change": `dedupe.js#computeFingerprint` (governs KV-level new/updated/duplicate) and `notified.js#computeNotificationFingerprint` (governs the actual per-target re-push decision). Building a separate OPEN/STOPPED state machine — its own KV key, its own transition logic, its own "have I already told this target about this state change" check — would duplicate machinery this pipeline already has working, tested, and battle-proven (see e.g. the accident incident-suppression layer's own escalation logic, which solves a structurally similar "same real-world thing, meaningfully changed" problem a different way for a different reason). One conditional key on two existing, well-understood functions gets the exact same guarantee (state change → re-push, same state+content → dedupe) with a two-line change and zero new failure modes to reason about.

### Why `resolveKmRange` reuses `resolveKmLocation`'s midpoint-and-bracket logic instead of independently finding the two facilities nearest each endpoint

"The two interchanges bracketing this whole range" and "the two facilities immediately before/after the range's own midpoint" are the same thing for any range short enough to plausibly describe one incident/event (a few km, never spanning multiple interchange gaps) — which is the only case this project's facility data can honestly answer anyway (`FREEWAY_FACILITY_MAX_GAP_KM` already fails closed for anything wildly far from a facility). Independently finding the nearest facility to EACH endpoint separately could, in principle, produce three or four different facilities for a range that straddles more than one interchange gap — a genuinely harder problem this project's facility data was never asked to solve, and the task's own real fixture (91K+590～93K+320, comfortably within one interchange gap) doesn't need it solved. Reusing the midpoint-based resolution `resolveKmLocation` already had, unchanged, both avoids that harder problem and guarantees `resolveKmRange`'s output can never independently drift from what the SAME event's own LINE message text already shows (both ultimately call the identical underlying resolution).

### Why the single-camera selector prioritizes "inside the range, closest to midpoint" over "closest to either endpoint"

A camera physically located somewhere within the event's own affected range is, by definition, showing the actual shoulder in question — there's no meaningful sense in which a camera nearer to `startKM` is "more representative" than one nearer to `endKM`, since both are inside the same real, physical stretch the shoulder-open/stop applies to. Ranking by distance to the midpoint (rather than, say, the earlier bulk of two competing conventions like "nearest to startKM" or "first candidate found") gives a stable, unambiguous single winner among multiple in-range candidates, and only falls back to the existing ±2km/±4km distance-from-midpoint rule (unchanged from how every OTHER camera search in this codebase already works) when nothing is actually inside the range at all.

### Why `single` mode publishes the raw fetched frame bytes directly, with no decode/re-encode step at all

The task's own performance requirement is explicit: "較少 decode/encode," and the cheapest possible interpretation that's still fully correct is zero — a single already-JPEG-encoded frame IS the final image; there is nothing to compose it WITH, so decoding it into pixels and re-encoding it back to JPEG would only spend CPU to produce a byte-for-byte-equivalent (at best; JPEG re-encoding is lossy, so a decode/re-encode round-trip could only make the image marginally WORSE, never better) result. `publishCollageImage` was already content-agnostic (it accepts and stores whatever `jpegBytes` it's given — see its own doc comment), so reusing it for a raw single frame required no changes to that function at all, and this decision costs nothing to implement while genuinely fulfilling "single 模式應比 quad 更省."

### Why `selectedCamera` on the Pipeline Trace entry is a minimal string, not the full CCTV metadata record

`pipelineTrace.js`'s own module comment already establishes a hard whitelist-only discipline — never a Secret, never a raw payload, only specific, deliberately-chosen fields (see `buildUpstreamSnapshot`'s own field list). A CCTV metadata record carries `VideoStreamURL` (an unauthenticated, directly-fetchable freeway.gov.tw stream endpoint) and coordinate data — neither is sensitive exactly, but storing the full record in a 24h-TTL debug log that's already established to store as little as possible, when a human diagnosing "why did this event's photo look wrong" only ever needs "which camera, roughly where" (`${cctvId}@${locationMile}`), would be scope creep against that discipline for no diagnostic benefit.

### [Correction round] Why the LINE 播報 timeline never used `identity.timestamp` as a stand-in for the push time

The temptation is real: `identity.timestamp` already exists, is always populated, and is close in time to a successful push (the trace entry is written at the end of the same pipeline run that did the push). But "close in time" and "the actual event being described" are not the same fact — `identity.timestamp` is when this TRACE ENTRY was recorded, not an attestation from the LINE send call itself, and this project's own inspected `pipelineTrace.js` schema confirms `delivery` never captured such a timestamp (`lineAttempted`/`lineSucceeded` are per-run counts only). Displaying it under a "LINE 播報" label would silently manufacture a precision the data doesn't actually have — the exact failure mode this project's "不要猜" rule exists to prevent, and precisely the kind of thing this whole Pipeline Trace feature exists to let an administrator catch, not commit. The honest fallback ("已播報（未保存獨立時間）") costs nothing and tells the truth; a wrong-but-confident timestamp costs nothing to write but could mislead an administrator debugging a real delivery-timing question later.

### [Correction round] Why no schema change was made to add a real LINE push timestamp

Adding `linePushedAt` (or similar) to `delivery` was considered and rejected for this round specifically, not as a permanent no: `recordPipelineTrace`'s own module comment establishes a hard boundary — "A trace write can NEVER affect the real pipeline outcome" — and the trace-build call sites (`broadcastPipeline.js`'s per-event loop, `scheduled.js`'s finalize pass) are on the Cron hot path already budgeted for exactly one KV `put` per event, no more. A schema addition here is easy to get wrong in a way that's expensive to notice (e.g. accidentally threading a wall-clock read into a place currently only touched by pure, already-computed values, or widening what "the same pipeline run's own already-computed values" means for every future field). The task's own instruction was explicit: only make this change if the cost is confirmed low and it adds no hot-path KV write, and even then keep it minimal with regression coverage — given the fallback text is genuinely accurate (not a degraded experience, just an honest one) and no other consumer of this schema asked for the field, the lower-risk choice this round is to report the gap truthfully and leave the schema decision for whenever an actual second consumer needs the value. `linePushTimestamp()` was still written to check for one, so the day this field IS added, the UI needs no further change.

### [Correction round] Why the relative list-time comparison uses Taipei calendar days, not elapsed hours

"今天"/"昨天" are calendar concepts, not duration concepts — a Taiwanese reader's own mental model of "today" flips at Taipei midnight, not 24 hours after any particular earlier timestamp. A naive `now - iso < 24h` check gets both edges of this wrong: two timestamps 20 minutes apart that straddle Taipei midnight (23:50 yesterday, 00:10 today) are on different calendar days and must read 昨天, while two timestamps nearly a full day apart but both before that midnight (08:05 and 23:55, same Taipei date) are still 今天. Computing `Date.UTC(year, month-1, day)` from each timestamp's own Taipei-shifted y/m/d and diffing THOSE (not the original instants) makes the comparison operate purely on calendar dates, matching how a human actually reads "今天"/"昨天", at the cost of one extra `taipeiParts()` call per row (already cheap, pure, no I/O).

## V1.8.7.1 — Multi-event Single CCTV Budget / Fairness Fix

### Why single-strategy events get their OWN clock instead of a bigger/smarter shared one

The tempting quick fix was to simply give single-strategy events a LARGER share of the existing shared `cctvRunDeadlineAt`, or to reorder the loop so singles go first (they already do) and hope that's enough. Both are still fundamentally "N things dividing one finite resource, in an order that determines who wins" — the exact structural shape that produced this bug in the first place, just with different numbers. A single frame fetch's cost doesn't scale with how many OTHER events happen to exist in the same tick (unlike, say, R2 storage cost or LINE API rate limits) — there's no real resource being shared here at all, only an artificial one (one shared clock) inherited from a mechanism (V1.8.5's quad budget-sharing) that was designed for a DIFFERENT problem: bounding N accidents' potentially-slow, potentially-highly-variable 4-frame-fetch-plus-compose cost. Giving every single event its own small, fixed, independent budget removes the "division" problem entirely rather than trying to divide more cleverly — the simplest fix that is also correct, per the task's own "選擇最簡單、最少技術債的方案" instruction.

### Why a fixed per-event budget (1500ms) rather than a budget proportional to remaining events

A proportional/dynamic allocation (e.g. "divide whatever's left by however many single events remain") sounds fairer in the abstract but reintroduces the exact coupling this fix removes: event N's budget would depend on how many events came before AND after it, making behavior harder to predict, harder to test (the same fixture would behave differently depending on how many OTHER events happen to be in the same tick), and reintroducing a shared-state calculation this bug already showed is easy to get wrong. A FIXED per-event budget means every single event's own worst case is independently knowable and testable in isolation — "does 1 single event work" and "do 5 single events work" are provably the same question asked N times, not N different questions.

### Why the cap is a COUNT (5 events) rather than a total-time budget for the whole single-event phase

A total-time cap for "all single events combined" would reintroduce shared-clock division between single events specifically — solving the accident-vs-single sharing problem while leaving the single-vs-single problem (the ACTUAL bug reported) unsolved in a subtler form (the 6th event competing with the 5th for whatever time remains, rather than for the whole 4s). A count-based cap, paired with each attempt getting its own FULL fixed budget, guarantees every event within the cap gets the complete, undiminished 1500ms every other event within the cap gets — true fairness, not merely "less unfair than before." The cost is a HIGHER worst-case total (`cap × per-event budget` can exceed a single shared window), which is the explicit, accepted tradeoff for genuine fairness — see the "5 comfortably covers 3" reasoning below for why this tradeoff was kept small.

### Why `MAX_SINGLE_CCTV_EVENTS_PER_RUN = 5`, not exactly 3 (Production's own evidence) or a much larger number

Exactly 3 would tie the safety cap to the ONE real data point this round has, with no headroom for a busier day producing a 4th or 5th genuine event — a cap that starts silently degrading the very next time reality exceeds the sample it was derived from is a fragile choice. A much larger cap (say, 20) would make the worst-case total delay (`20 × 1.5s = 30s`) a real, uncomfortable fraction of typical Workers scheduled-event wall-clock limits, for a scenario (20 simultaneous dynamic-shoulder events on one short freeway stretch) this project has no evidence ever occurs and no product reason to specifically provision for at full cost. 5 sits deliberately between these: comfortable headroom over the one real data point (3), while keeping the worst-case addition (7.5s) a small, bounded, easily-reasoned-about number — explicitly not derived from exhaustive load testing (this sandbox cannot reach the real Cloudflare Workers runtime), but from the same "reasonable, documented, adjustable if reality disagrees" spirit the task's own "自行決定" instruction asked for. Both constants are exported, named, single-source-of-truth values — trivial to retune later against real Production telemetry without touching any call site.

### Why `'prepare-timeout'` was reused for a single event's own budget expiring, instead of a new distinct reason string

The task's own §5 offered two acceptable reason strings — `single-event-cap-reached` OR `run-budget-exhausted` — for the two failure modes it wanted distinguishable ("安全上限" vs "真的時間耗盡"). `'prepare-timeout'` already existed in this codebase, already means exactly "this one call's own timeout elapsed" (it's the SAME reason `withTimeout`'s losing race already produces for the quad path), and is already just as distinguishable from `'single-event-cap-reached'` as a brand-new string would be — a Pipeline Trace reader sees one of two clearly different words either way. Inventing a THIRD reason string (a `'single-run-budget-exhausted'` or similar) to shadow an existing, semantically-identical one would be exactly the "複製相同規則到多個地方" this project's own standing discipline warns against, for zero added clarity.

### Why quad's own deadline was made lazy rather than left anchored at loop-start

Leaving `cctvRunDeadlineAt` anchored at loop-start (unconditionally, before either strategy is considered) was the ORIGINAL, correct-at-the-time design — but this round changed a load-bearing assumption underneath it: dynamic-shoulder events now always run BEFORE accidents in the same loop, and previously consumed a shared clock too, so their processing time was always implicitly "spent before the clock that mattered" either way. Once single events got their OWN independent budget (this round's whole point), their processing time no longer belongs to any clock accidents care about — except it still silently ate into `cctvRunDeadlineAt`'s real wall-clock countdown purely because that countdown started ticking before the loop even knew which events were which. Lazily anchoring the deadline to the moment accident-CCTV processing itself begins is the minimal fix that restores the ORIGINAL intent (an accident's own nominal 4-second window, undiminished by anything unrelated to accidents) without touching the deadline's VALUE, its accident-vs-accident sharing behavior, or any of the quad pipeline's own internals — exactly "不要為了 dynamic shoulder 把 accident quad 的 deadline 無限制放寬," read as "don't let this round's OWN change shrink it either."

### Why Pipeline Trace got `singleSlotIndex`/`singleSlotLimit`/`cctvBudgetClass` instead of the task's own example `budgetAtStartMs`/`budgetRemainingMs`

A millisecond remaining-budget number requires the reader to already know (or go look up) `SINGLE_CCTV_PER_EVENT_BUDGET_MS`/`CCTV_PREPARE_BUDGET_MS` to interpret it — "312ms remaining" means nothing without that context. "This was slot 6 of a 5-slot single-per-event cap" is self-explanatory on its own: an administrator immediately understands both WHAT happened (over the cap) and WHY (the 6th of only 5 allowed slots) without cross-referencing a source-code constant. `processingDurationMs` (how long the attempt itself took) is the one piece of genuinely time-based information worth keeping, since — unlike a budget/remaining pair — it's a fact about what actually happened, not a number requiring reconstruction of the budget math to interpret.

## V1.8.7.2 — Dynamic Shoulder Message Simplification

### Why the removed safety-reminder sentences were treated as a TEXT decision, not a safety-policy decision

"請依現場標誌及號誌行駛" and "請回主線車道" were never the thing that made a driver's shoulder use lawful or safe — the physical signage/signals at the scene, and the driver's own compliance with them, always were; the LINE message was only ever a secondary reminder of an obligation that exists independently of whether this Worker mentions it. Removing the sentence changes what this Worker SAYS, not what's legally/physically true on the road, so this is squarely a message-length/clarity decision within this round's stated scope ("只改 dynamic shoulder LINE 訊息") — not a change to any safety rule, gate, or eligibility this codebase enforces. Nothing about `broadcastRules.js`'s eligibility, `dynamicShoulderClassification.js`'s state detection, or any other decision-making logic changed; only the WORDING of an already-informational message did.

### Why the map line was removed for dynamic-shoulder specifically but the underlying resolver stays fully intact for everyone else

A shoulder-open/stop report's most useful piece of location information is already IN the text — the official interchange section label and the KM range together tell a driver "roughly here, this stretch" without needing to tap a link. An accident or construction report, by contrast, often needs the PRECISE point (which exact interchange approach, which exact KM the incident sits at) that only a map pin conveys unambiguously — a genuinely different need this round's task never asked to change. Removing `mapLine` from ONLY the dynamic-shoulder branch (an early return that never touches the shared `buildRoadLines()`/`resolveKmLocation()` machinery) means every other event type's map line, and the resolver functions that produce it, are provably unaffected — verified directly by keeping `kmLocationResolver.js` in the zero-diff set for this round and re-testing accident/construction's own exact byte-for-byte formatter output.

### Why the updated-time line was removed rather than kept "just in case"

The task's own reasoning was already sound and is worth restating plainly: LINE's own message metadata already timestamps every message a recipient receives, so a "🕒 XX:XX更新" line inside the text is redundant information for a LIVE, real-time status flip specifically (as opposed to an accident/construction report, where "更新" answers a genuinely different question — when the SOURCE record was last refreshed, which can legitimately differ from when THIS push happened, e.g. a duplicate/re-broadcast scenario). A dynamic-shoulder push only ever fires on a real state CHANGE (see V1.8.7.0's own fingerprint design — OPEN↔STOPPED is the only thing that triggers a re-push), so "when was this last updated" and "when did I receive this message" are the same fact for this event type, making the line pure redundancy rather than added clarity — worth cutting under this round's own "降低洗版" goal, with no engineering reason found to keep it.

### Why the early-return short-circuit, instead of threading a "short mode" flag through the existing line-assembly code

`formatEventMessage`'s existing body builds `emoji`/`label`/`impactLines`/`mapLine`/`updatedHHMM` as a sequence of ternaries feeding one final `lines.filter(Boolean).join('\n')` — adding a "skip mapLine/updatedHHMM for dynamic-shoulder" condition to EACH of those ternaries would touch the same shared code every other event type depends on, in multiple places, for a behavior that's actually specific to one event category and needs nothing else that machinery computes. An early return keeps the change fully localized (one new `if` block, returning before any of the shared ternary logic even runs) and makes the boundary between "dynamic-shoulder's own rules" and "every other event type's shared rules" a single, obvious line in the function — the same reasoning V1.8.7.0's own original dynamic-shoulder branch used, taken one step further now that dynamic-shoulder's own template no longer shares ANY trailing lines with the generic template it used to reuse partially.

## Shared Traffic Feed — Producer/Consumer Authority Boundary

### Why traffic-reporter never edits a consumer repository, even to fix a bug the consumer clearly has

The Shared Traffic Feed's entire value proposition is that a consumer can trust `completedProducts` without re-deriving it — TDX/PBS ingestion, classification, eligibility, dedupe, time-window rules, formatting, and CCTV all happen exactly once, in this repo, and every consumer sees the same already-judged answer. That guarantee only holds if the AUTHORITY for "what should be broadcast and what it should say" stays in exactly one place. Reaching into a consumer's own codebase to patch a transport-layer bug there — even with good intentions, even if the fix is obvious — would blur that boundary in practice (now two repos' worth of logic ship un-reviewed-by-the-other-team into what's supposed to be one team's product) and set a precedent that "the Producer session will just fix it" instead of the consumer's own maintainers/session doing so with their own context, their own tests, and their own deploy authority. The correct action when a consumer-side symptom appears is to gather and hand across evidence — a Pipeline-Trace-style reproduction, exact request/response pairs, a suggested diff described in prose — and let the actual owner of that repository apply it.

### Why the feed stays generic instead of gaining "is this what 雙鐵 wants" logic

The moment the Producer starts asking "would THIS consumer want this event" it has silently taken on a SECOND authority role — not just "what happened and how to describe it" but "who gets to see it" — which fragments the single-source-of-truth guarantee the feed exists to provide. A future second consumer would then need the Producer to grow a second branch of the same kind of logic, and the two consumers' own business rules (which the Producer has no way to know, validate, or keep in sync with their own product decisions) would end up encoded in a repository neither of them owns. Keeping the feed a single generic `completedProducts` stream — same content, same shape, to whoever reads it — means each consumer's own subscription/filtering logic lives where it belongs: in that consumer's own code, which can iterate on its own preferences without ever needing a Producer-side change.

### Why `offset` was added to `selectFeedWindow` rather than building a cursor/token-based pagination scheme

A numeric offset into a deterministically-sorted (`updatedAt` desc, `eventId` asc) list is the simplest mechanism that satisfies every real requirement here: a consumer can request any page independently (no dependency on having seen a previous page's response first, unlike an opaque cursor), the ordering is stable within one snapshot (so a page-by-page walk during one read pass has no gaps/overlaps), and cross-snapshot drift (a page boundary shifting slightly if the underlying window changed between two of the consumer's requests) is explicitly accepted as harmless — a Shared Feed consumer already re-reads the WHOLE window on every round and dedups its own deliveries by `eventId`+fingerprint (this project's own transport layer never needed to solve that; it's the consumer's job, as the task's own instruction restates), so a rare, small page-boundary shift costs at most a duplicate the consumer's own dedup already absorbs. A cursor/token scheme would add real complexity (opaque state to generate, validate, and expire) to solve a consistency problem this feed's own architecture doesn't actually have.

### Why `isTargetRoad`'s fix makes RoadID authoritative rather than requiring BOTH fields to agree

Requiring both RoadID AND RoadName to agree (a stricter AND, rather than "RoadID wins when present") would also close the cross-contamination gap, but at a real cost this round's own evidence argues against: TWO of the three real dirty-data patterns reported (RoadID:'000030'+RoadName:'國道1號', and the reverse) have a CORRECT field and a WRONG field, not two independently-untrustworthy fields — RoadID is the more specific, structured identifier (a fixed code TDX presumably assigns per road, unlikely to be freely mistyped by whoever entered `RoadName`, a free-text field), and treating it as authoritative when present correctly RECOVERS these records into their true road's pool rather than excluding them from both (which an AND-both-must-agree rule would have done, silently shrinking 國1's own real candidate pool by throwing away a real, correctly-RoadID'd 國3 camera's own presence check — wait, more precisely: an AND rule would have excluded the dirty record from EVERY road's pool, including its own true one, since one of its two fields always disagrees by construction). Keeping the existing fallback, demoted rather than deleted, costs nothing today (it's not exercised) and preserves a real safety net for a data-quality failure mode this same investigation already demonstrated this feed is capable of producing.

A 國3-specific patch — e.g., a hardcoded exclusion list of the specific dirty CCTVIDs the inspection happened to report, or a special-cased check only active when `roadId === '000030'` — would fix exactly the symptoms this one inspection happened to surface, and nothing else: a future third road, or a future different dirty record the same inspection didn't happen to sample, would hit the identical class of bug with no protection. The task's own explicit instruction ("禁止為單一 102K hardcode" / "請做最小且通用的 matching 強化") already states this principle; the decision worth recording is WHY the general form was still the right level of generality to reach for, not a narrower or broader one — narrower (per-road) reintroduces the exact kind of special-casing this project's registries (`CCTV_SUPPORTED_ROADS`, `ROAD_ALIASES`, etc) are all deliberately built to avoid needing; broader (e.g., a full data-quality validation/cleaning layer over the entire metadata cache) would be solving a problem this round has no evidence is bigger than the one specific ambiguity class (RoadID vs RoadName disagreement) actually reported.

## V1.8.7.3 — CCTV Prepare-Timeout Fix + Pipeline Trace Filter Fix

**Integration note**: designed/reasoned about against an older `main`, predating V1.8.7.4/V1.8.7.5 above — cherry-picked cleanly onto current `main` with 0 code conflicts (see `PROJECT_HANDOFF.md` §33). Every decision below stands unchanged; none of it concerns 國3 or `isTargetRoad`, so nothing here interacts with the two sections above.

### Why the new budget number (6000ms) is grounded in `FRAME_TIMEOUT_MS`, not chosen freeform

This sandbox has no TDX/freeway.gov.tw network egress, and this round was explicitly forbidden from making a real probe — so there is no way to derive a new number from a fresh real-world latency measurement taken during this round. Picking an arbitrary "big enough" number (say, doubling to 3000ms, or an unmotivated round 5000/10000) would have been just as much a guess as the original 1500ms evidently was. `tdx/hsinchuCctvProbe.js`'s own `FRAME_TIMEOUT_MS = 5000` is the one piece of real, already-accepted-into-this-codebase evidence available: it's the SAME function, against the SAME class of URL, already given that ceiling elsewhere in Production-adjacent code (the admin single-frame probe). Anchoring the new budget to that existing constant (plus headroom for R2 publish/overhead) means the choice is falsifiable and cross-checkable — a future round with real Production telemetry can directly compare "did single-CCTV frame fetches actually cluster near 5000ms" against this stated assumption, rather than reverse-engineering what a bare "6000" was ever supposed to represent.

### Why `MAX_SINGLE_CCTV_EVENTS_PER_RUN` was left at 5 instead of being lowered to offset the bigger per-event budget

Lowering the cap would trade "spurious timeouts on legitimate frame fetches" for "more events skip CCTV outright, deterministically" — replacing one form of missing-image problem with another, and doing so pre-emptively without any Production evidence that 5 events' worth of worst-case 6-second slots (30s total) is actually a problem for Cloudflare Workers' scheduled-event execution model. The dimension Workers actually meters and limits is CPU-active time, not wall-clock time — and virtually all of the added worst-case time here is spent awaiting network I/O (fetch/KV/R2), which does not count as CPU-active. Since V1.8.7.1 already established 5 as "comfortable headroom over the one real data point (3 events/tick)," and this round's own Production evidence still shows the same order of magnitude of events per tick, there was no signal to justify moving that number in either direction — only the PER-EVENT duration needed to change, because that was the number the evidence (the FRAME_TIMEOUT_MS mismatch) actually pointed at.

### Why `timeoutStage` is captured via a mutable tracker object read lazily, not passed as a static value

The natural-looking first draft — build the timeout fallback value once, right where the race is set up (`withTimeout(work, budgetMs, {..., timeoutStage: stageTracker.stage})`) — reads as correct but is subtly wrong: JavaScript evaluates that object literal's properties immediately, at the line where it's written, not lazily at the moment the timer actually fires. Since `work` has barely begun by the time that line runs (it's still mid-`await` on the very first async step), the captured value is always whatever stage was current at RACE SETUP, not at RACE RESOLUTION — for this code, always `'metadata'`, regardless of where the timeout genuinely caught the work in flight. This is exactly the kind of bug that looks plausible, compiles, often even passes a shallow test (if the test doesn't independently verify against a KNOWN-different stage), and was only caught here because a test specifically engineered a slow FRAME fetch and asserted the reported stage matched. The fix — race a unique sentinel, then construct the timeout-branch result object only after the race resolves — is the general pattern for "report live state at the moment an async race is lost," worth restating here because the same shape (constructing an object eagerly that's meant to describe a LATER moment) is an easy mistake to reintroduce in any future addition to this same `withTimeout` idiom.

### Why `frameFetchDurationMs` measures fetch+body-read as one number, not two

`extractFirstJpegFrame` (in `tdx/hsinchuCctvProbe.js`) is a single already-ratified, shared function — used unchanged by both the quad (accident) and single (dynamic-shoulder) CCTV paths — that internally does one `fetch()` followed by one streaming body-read loop (scanning bytes for JPEG start/end markers) inside one `try` block, with no natural seam between "connect" and "read" exposed to callers. Splitting those into two separately-timed sub-stages would require modifying that shared function's internals — building, in effect, a parallel/modified frame-fetch implementation for the dynamic-shoulder path alone, which is precisely what this project's own standing "不要為 dynamic shoulder 建第二套 CCTV pipeline" principle (established in V1.8.7.0, reaffirmed every round since) rules out. A single combined number is a legitimate, honest measurement of "how long did getting one frame from the camera actually take" — coarser than a two-way split, but truthful, and it does directly answer this round's own actual question (is frame-fetch, as a whole, the dominant cost) without introducing new risk to a shared, already-tested code path.

### Why the Pipeline Trace filter fix separates "how many list() PAGES to scan" from "how many keys to then read+filter" instead of just raising `MAX_ENTRIES_SCANNED`

The tempting one-line fix — just raise `MAX_ENTRIES_SCANNED` itself, e.g. to 2000 — conflates two genuinely different questions that happened to share one number by accident: (1) how far into the 24h key range does the cheap key-ENUMERATION pass need to walk to find the truly newest keys, and (2) once found, how many of those newest keys is it worth actually paying a `kv.get()` for. Raising the shared constant would fix (1) only as a side effect, while ALSO inflating (2) far beyond what's needed — every filtered query already only wants at most `MAX_LIST_LIMIT` (100) results, so reading 2000 full records to satisfy a 30-100-record page is pure waste with no benefit, the exact kind of accidentally-coupled-constants bug this fix exists to eliminate, not reintroduce in a different shape. Two independently-named, independently-reasoned constants (`MAX_LIST_PAGES` for cheap key enumeration, `MAX_ENTRIES_SCANNED` — unchanged — for the more expensive get+filter step) make each one's actual job legible from its own name and comment, and make a future retune of either one (e.g. if 24h volume grows) obviously safe to do independently, without having to first re-derive which of two unrelated concerns the single old constant was actually protecting.

### Why `MAX_LIST_PAGES = 40` rather than removing the page cap entirely (always paginate to `list_complete`)

Removing the cap outright would make the enumeration pass's own cost fully proportional to whatever the real key count happens to be, with the only bound being however wrong the underlying data ever gets (e.g. a hypothetical future TTL/pruning regression leaving far more live keys than this module's own documented volume expectation). The real termination condition, in the normal case, is already `page.list_complete`/`!page.cursor` — `MAX_LIST_PAGES` is never expected to be hit in ordinary operation; it exists purely as the same kind of defensive ceiling this project already applies everywhere else a KV scan could in principle run unbounded (`MAX_ENTRIES_SCANNED` itself, `broadcastProvenance.js`'s own scan bound). 40 pages, at a realistic ≥500-1000 keys/page, comfortably covers tens of thousands of keys — an order of magnitude beyond this module's own stated worst-case daily volume ("low tens of events × every ~10-minute tick") — while still guaranteeing the Admin-triggered, on-demand read endpoint this protects can never become genuinely unbounded no matter how badly some future, unrelated bug inflates real key counts.

## V1.8.7.6 — Pipeline Trace Filter Production Investigation

### Why "no defect found" was reported as the honest conclusion, not treated as a failure requiring a fabricated fix

This project's standing "不要猜" (don't guess) discipline applies just as much to ROOT CAUSES as it does to data values — asserting a plausible-sounding but unverified explanation ("probably a caching issue" stated as fact, or worse, inventing a code change that LOOKS like a fix but doesn't correspond to anything actually wrong) would be strictly worse than an honest negative result, because it would give the impression a bug was found and fixed when nothing was actually confirmed broken — the single most misleading outcome a debugging round can produce. Three escalating reproductions, including one driven by a REAL browser executing REAL DOM interactions, is a materially higher bar than most bug investigations get to clear; concluding "the code, as far as every mechanism available to this session could exercise it, is correct" is itself a complete, useful, evidence-backed deliverable — it tells the next person exactly what has already been ruled out, so effort isn't wasted re-treading this same ground.

### Why the active-filters banner was built instead of, say, adding more logging

A server-side log line is invisible to the admin reporting the bug in real time on their phone — they'd need to separately ask someone to go pull logs, introducing a delay and a dependency this project has repeatedly tried to eliminate for exactly this kind of "why did the page show that" question (see e.g. Pipeline Trace's own original 2026-08-19-ish motivation: "let a non-programmer administrator look at ANY event... without needing a fresh TDX/PBS query to answer"). Printing the ACTUALLY-APPLIED filter values directly in the page the admin is already looking at means the very next time this is reported, the diagnostic information is already sitting on their screen — no log access, no second round-trip, no "can you send me a screenshot of the URL bar" (which many admins on mobile Safari can't easily do without truncation anyway, since the address bar often only shows the domain). It also has a second, quieter benefit: even absent a bug report, it lets an admin doing routine spot-checks immediately confirm "yes, I'm looking at exactly the slice I meant to look at" — closing a small trust gap the plain `<select>` state alone (visible only by re-opening the dropdown) didn't fully close.

### Why the cache headers were strengthened even without proof caching is the actual cause

This is a calculated, asymmetric bet: if caching is NOT the cause, the extra `Cache-Control`/`Expires` directives cost nothing (every browser and intermediary already respects `no-store`, an already-present header, correctly — the additional directives are redundant-but-harmless reinforcement of the exact same instruction, not a new behavior). If caching IS the cause, this may directly resolve the symptom for real users without needing to wait for a client-side architecture change this round is not authorized to make. Given the tests overwhelmingly point away from a server logic defect, spending a few bytes of response headers on a plausible, zero-risk, zero-regression mitigation is a better use of this round's remaining scope than either doing nothing or forcing a speculative change to `listPipelineTrace`'s own (already-reverified-correct) filter logic.

### Why a real headless-browser reproduction was built at all, given the cost/complexity

Every previous round's Pipeline Trace investigation (including §33's own root-cause-finding one) reproduced bugs by calling `handlePipelineTraceView` directly with a hand-constructed `Request` — sufficient for finding §33's actual bug (a KV-layer pagination defect, invisible to any HTML-layer difference), but NOT sufficient to fully rule out a markup-level or real-browser-mechanics-level defect, which is exactly the category of bug this round's report was most consistent with (server logic re-verified correct via direct testing; the remaining unknown was specifically "does a REAL browser's OWN form-submission behavior match what a hand-built Request assumes"). Since Playwright and a Chromium binary were already present in this environment (installed globally for other uses), building this reproduction cost relatively little and closed the one investigative gap a purely code-level/hand-built-Request approach could never fully close — worth doing specifically BECAUSE this round's task explicitly demanded not assuming any layer, including the browser-facing one, was already correct.

## V1.8.7.7 — CCTV Gray Broken Image Fix (Dynamic-Shoulder Frame Truncation)

### Why root cause was pursued via static code analysis rather than deferred pending live evidence

This round's authorization explicitly forbade defaulting to any of the obvious surface explanations (LINE blocking, R2 broken, URL expired) and required tracing the full chain to a genuine root cause. This session's sandbox has zero network egress (confirmed via `curl` returning `403` from the environment's own proxy for both the Production Worker's hostname and general internet hosts) and no Cloudflare credential of any kind — so, unlike §32's real-Production-KV-inspection-informed round, there was no live evidence path available at all this round, not even a read-only one. Waiting for live evidence was not an option consistent with the authorization's "自主查明 Root Cause → 修復 → 測試 → 驗證" instruction and its explicit prohibition on excessive check-ins. The alternative actually taken — full static trace of the real code path, cross-referenced against this codebase's OWN pre-existing engineering comments (specifically `collage.js`'s comment already anticipating "a cell can fetch a 200 that isn't a valid/decodable JPEG," which is the exact tell that pointed at frame validity rather than transport/storage/expiry) — produced a root cause that is falsifiable and was in fact directly verified: 12 new tests reproduce the failure mode against the pre-fix code (all 5 embedded-thumbnail-relevant tests fail) and pass against the fix. A root cause established this way, with tests that fail on the old code and pass on the new code, carries real evidentiary weight even without a live Production log citation — the honest caveat (disclosed in `PROJECT_HANDOFF.md` §35) is that it wasn't cross-checked against an actual captured Production frame, because no such frame could be fetched from this sandbox.

### Why the fix touches the shared `extractFirstJpegFrame` rather than only adding a decode-validate step to the single-camera path

Two fix shapes were considered: (a) fix the actual marker-scanning defect in the shared frame-boundary function, or (b) leave the naive scan alone and instead add a decode-through-`@jsquash/jpeg`-to-validate step specifically to `prepareSingleCctvImageWork` before publishing, mirroring how the quad path incidentally gets this protection today. (b) was rejected: it would have reintroduced exactly the JPEG decode/encode cost V1.8.7.0 deliberately eliminated for the single-camera path's own stated performance reason ("one frame IS the final image," no round-trip) — paying that cost on every single-camera event just to catch a specific, nameable byte-scanning bug is symptom-masking, not a root-cause fix, and the authorization for this round explicitly said "優先修 Root Cause，不要用 symptom masking." (a) — fixing `extractFirstJpegFrame` itself to correctly locate a JPEG's real EOI — costs nothing extra at runtime (still a single streamed read, no decode), fixes the defect for EVERY current and future caller (the fixed-target admin frame endpoint, the quad path's frame fetches, and the single path all share this one function), and is the more honest fix: the bug was never really "the single path doesn't validate enough," it was "the frame-boundary detector was wrong," and quad's decode step only ever hid that, it didn't fix it.

### Why a full JPEG marker walker was written instead of a simpler heuristic (e.g. "use the LAST FFD9 instead of the first")

A simpler-looking alternative was considered and rejected: instead of properly parsing marker segments, keep reading further and take the LAST `0xFFD9` found before the next MJPEG frame's own SOI (or before giving up), on the reasoning that a real image's own terminal EOI always comes after any embedded thumbnail's EOI. This was rejected for a concrete, testable reason: `extractFirstJpegFrame`'s own existing, already-passing regression test (`test/hsinchuCctvProbe.test.js` test 7, "captures exactly the first complete JPEG frame and stops reading the stream") explicitly asserts the function must stop and cancel the stream the INSTANT a complete frame is found, and hangs the test (by design) if a 3rd stream `pull()` ever happens — meaning any fix that requires reading further into (or past) the NEXT frame to confirm "this was really the last FFD9" would break that existing, deliberately-strict invariant, which exists to avoid ever mixing bytes from two different MJPEG frames together. The marker-segment walker chosen instead needs bytes only from WITHIN the current frame's own header segments and scan data — it never needs to peek at what comes after the real EOI — so it's fully compatible with "stop immediately once found," not merely a looser approximation of it.

### Why a fallback to the old naive scan was kept, rather than making the walker strict everywhere

Making `findJpegImageEnd` strict (fail/wait forever on any non-marker-structured input) would have silently broken this module's OWN pre-existing test suite, which uses a deliberately simplified byte sequence (`[0xff,0xd8, 1,2,3,4,5, 0xff,0xd9]`, no real marker segments at all) to stand in abstractly for "a complete JPEG frame" when testing unrelated behavior (stream-stopping, timeouts, size caps, hostname trust). Rewriting every existing test fixture across this module's test suite to use byte-perfect real JPEG marker structure, just so an internal helper function could be marginally simpler, was rejected as unnecessary blast radius for a round whose actual authorized scope is the frame-truncation bug — not a refactor of this file's entire test fixture convention. The fallback is precisely scoped (fires only when the buffer, at an already-fully-received position, genuinely isn't marker-structured — never when more streamed bytes are simply still arriving, which always resolves as "wait for more data" instead) and is not expected to ever engage against real freeway.gov.tw camera output, which is always well-formed.

### Why "the accident quad path was never at risk" was verified, not assumed

It would have been easy to simply assert "the quad path decodes frames so it's fine" without checking — but `collage.js` was read in full specifically to confirm this, and its own pre-existing comment (not new text written to support this round's narrative — an already-existing engineering note) states outright that a fetched-but-undecodable frame is expected and handled by falling back to a placeholder tile, never propagated to a real user. This is cited directly in `PROJECT_HANDOFF.md` §35 as the actual evidentiary basis for the "quad was never at risk" claim, rather than treating it as self-evident from the architecture alone.

## Meeting Room Engineering Memory v1

### Why 02_PROJECT_HANDOFF.md and 04_PRODUCT_DECISIONS.md are verbatim copies, not separate curated summaries

Every other export file is a hand-authored template because no single existing repo file already covers that exact scope (a governance summary, a code-derived architecture overview, a cross-project boundary focus, a curated version line, a known-issues digest). `PROJECT_HANDOFF.md` and `PRODUCT_DECISIONS.md` are different: they already ARE the canonical Source of Truth for full history and design rationale. Writing a second, "condensed" version of either by hand would create exactly the kind of second, independently-maintained copy this project's own engineering culture has repeatedly flagged as a drift risk elsewhere (e.g. `isTargetRoad`'s "never a second, independently-guessed copy" reasoning, `composeCollageFromCandidates`'s shared-orchestration-path reasoning). Copying verbatim at export time costs nothing extra to keep in sync — it's re-read from the real file on every run — and guarantees the export is never stale relative to the repo it came from.

### Why narrative fields default instead of failing when unset

`CURRENT_TASK`/`NEXT_ACTION`/`KNOWN_BLOCKER` etc. cannot be derived mechanically the way a git SHA can — they require judgment about what's actually going on this round. Requiring an operator to always supply every env var before `finalize:release` would work but would make the tool fragile to forget-to-set mistakes, and a FAILED export because a narrative field was merely unset would be a worse outcome than a slightly-generic-but-still-true default (e.g. "None in progress — awaiting next assignment" is always at least honestly non-committal, never wrong). Defaults are grounded in the actual last-known state (e.g. `KNOWN_BLOCKER` defaults to referencing the latest release's real confirmation status, not a placeholder), and can be overridden per-run without editing the script — the safer failure mode is "slightly generic but true," never "export refuses to run."

### Why Drive sync failure can never fail `finalize:release`

Two independent reasons converge on the same design: (1) this round's own explicit instruction said so directly ("如果 Drive 暫時離線：Repo 封版仍算成功... 不能因此丟失本機工程紀錄"), and (2) the repo-committed `meeting-room-export/` is already a complete, durable, versioned record the moment it's committed — Drive is a convenience mirror for tools (like a ChatGPT Project) that can't clone a git repo, not a second source of truth. Making a release's success depend on a third-party sync target that this process may have zero access to (proven this round: a cloud sandbox literally cannot reach a user's local Windows Google Drive folder) would make "did we finish the release" depend on something structurally outside this session's control — the wrong thing to gate on.

### Why the Windows-path-on-non-Windows case is refused outright rather than merely warned

Real testing this round (not speculation) showed that WITHOUT this check, the sync script would report `GOOGLE_DRIVE_SYNC=SUCCESS` after writing 10 files into a meaninglessly-named local folder that is NOT the user's Google Drive — a false positive strictly worse than an honest failure, because a false "SUCCESS" is the one outcome that actively hides the problem from whoever reads the release summary next. A warning-but-continue would still have produced that same misleading SUCCESS status; refusing outright with an explicit reason is the only design that can't be misread as "it worked."

## V2.0.0 — Cloudflare Workers AI Driver-Impact Judgment Replaces Accident-Only as the Windows PBS Semantic Authority

### Why the product question changed from "is this an accident?" to "will this affect a working driver's ability to get through?"

Every hard rule this Windows PBS path retired — `MAJOR_ACCIDENT_ONLY`, the V1.5 type/keyword whitelist, `resolveLocationQuality`'s hard-reject — was, underneath its own specific mechanics, answering the same question: is this event's TYPE (accident vs. construction vs. control vs. congestion) one the product has pre-decided is worth a proactive LINE push? That question was never actually what a taxi/for-hire driver needs answered. A full closure for a military exercise, a rockslide, or a multi-hour lane-and-shoulder traffic control can matter just as much as a collision — and a briefly-blocking, quickly-cleared minor accident can matter less than a real closure that isn't legally an "accident" at all. Type-based rules were always a proxy for driver impact, adopted because the alternative — actually judging real-world consequence from free-text PBS comments — needed either a human reviewing every event in real time (not viable at PBS's volume/latency) or a semantic judge. Cloudflare Workers AI becoming available and affordable (see `07_KNOWN_ISSUES.md`'s neuron-cost estimate — a few percent of the free daily allowance at realistic volume) is what made answering the REAL question, instead of the proxy, viable for the first time. This is why the round explicitly forbade the AI prompt from mentioning accident/construction/control vocabulary at all (`src/pbs/aiDecisionEngine.js`'s own `SYSTEM_PROMPT`) — reproducing the old type vocabulary in the new judge's prompt would have just re-implemented the same proxy with an LLM doing the type-matching instead of a whitelist.

### Why this is scoped to the Windows PBS path only, not applied to TDX or retroactively to the old PBS polling path

TDX's own `runLineBroadcast` policy (`MAJOR_ACCIDENT_ONLY`/`getBroadcastEligibility`/`resolveLocationQuality`) continues completely unmodified — those functions were never deleted, only bypassed for the specific candidate-construction path Windows-sourced events now take. Two reasons converge: (1) changing TDX's decision logic was never authorized by any of the V1.9.9 phases' own explicit scope — each phase's own "禁止事項" section named this boundary directly; widening it on this round's own initiative would be exactly the kind of unauthorized scope creep this project's engineering culture has repeatedly flagged elsewhere (see e.g. the KV Write Optimization round's own TDX-untouched discipline). (2) A single new judge replacing an old one is a controlled, one-generation change with a clean kill switch (`PBS_AI_DECISION_ENABLED`) and a clean rollback (flip the switch, the legacy path runs byte-identical to before); simultaneously changing TWO independent decision paths (TDX's and Windows PBS's) to the same new judge would have doubled the blast radius of a single AI response quality issue, with no way to isolate which path a bad LINE push came from. Retrofitting the AI judge onto the retired Cloudflare 30-minute PBS polling path was never on the table either — that path is explicitly retired (not just superseded), its code kept solely as a fallback if Windows Local Edge itself fails, not as a second production decision path to also carry AI risk.

### Why the AI verdict is the sole authority for this path — never "AI plus the old rules," never "AI as an extra filter on top"

A design where AI approval is REQUIRED but the old hard rules still get a veto (i.e., AI says notify=true, but `MAJOR_ACCIDENT_ONLY` still has to also agree) was considered and rejected: it would silently re-introduce the exact type-based proxy this round exists to retire — a real closure from a non-accident event type would get AI approval, then get vetoed by the exact rule this change was meant to bypass, defeating the entire point while giving the appearance of having adopted AI judgment. The reverse design — AI as an additional filter that can only narrow, never widen, what the old rules already allow — has the same flaw in the opposite direction: it caps the new judge at the ceiling of the old proxy's coverage, so nothing new could ever get approved that wasn't already type-whitelisted, again defeating the purpose. The only design that actually answers the real question is the one built: for the Windows PBS candidate path specifically, a validated AI notify:true is sufficient on its own (subject only to genuine execution-safety gates — broadcast hours, LINE dedupe, CCTV/Shared Feed safety — never a second content judge), and an AI notify:false or any AI failure is 0 LINE with no fallback to the old rules, so there is never a case where two different judges could each veto or approve the same event by different logic (the "two judges for the same event" risk named explicitly in `src/pbs/debugPush.js`'s own mutual-exclusivity comment).

### Why "impact HIGH/LOW" was kept even though only `notify` gates the LINE push

`impact` is not currently used to change LINE behavior — a `notify:true` pushes regardless of whether `impact` is `HIGH` or `LOW`. It was kept in the schema anyway for two forward-looking reasons that were real at design time, not speculative feature creep: (1) `07_KNOWN_ISSUES.md`'s own recorded direction for a future hourly reminder on long-running major incidents needs exactly this signal to decide which cached AI verdicts are worth re-surfacing — building the schema to already carry it means that future work reads an existing cached field instead of needing a second AI call or a schema migration; (2) `impact` is genuinely part of what the model is being asked to judge in the first place (driver-impact, not just a binary "notify or not") — dropping it from the schema would have meant discarding information the model already had to reason about to answer `notify` correctly, for no cost saved (the same JSON response carries it at effectively zero extra token cost, since `reason` already has to explain the same reasoning in prose).
