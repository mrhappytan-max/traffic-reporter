### The dirty-data fix — general, not 102K-specific

The same Production inspection reported a real, if small, amount of label noise: some records' `RoadID` disagrees with their own `RoadName` (`RoadID:'000030'` + `RoadName:'國道1號'` — 1 record; `RoadID:'000010'` + `RoadName:'國道3號'` — 2 records; several other RoadIDs also carrying `RoadName:'國道3號'`). `tdx/hsinchuCctvProbe.js`'s `isTargetRoad()` used to be `recordRoadId === roadId` OR `roadNamePattern.test(roadName)` — an inclusive OR across two independently-populated fields. With only ONE road registered (國1, pre-V1.8.7.5), a record's RoadName disagreeing with its RoadID could at worst wrongly ADD an unrelated camera to 國1's pool (if that record's RoadName happened to match 國1's pattern) — annoying, but every 國1-search-relevant real record has always carried the correct `RoadID:'000010'`, per the pre-existing audit note, so this was latent, never triggered. With TWO roads registered, the SAME OR rule creates a genuinely different, sharper risk: a single physical camera's metadata record can now satisfy BOTH roads' `isTargetRoad()` checks simultaneously (matching one road by RoadID, the other by its own mismatched RoadName) — real cross-road contamination, where a 國1 incident search could return an actually-國3 camera, or vice versa.

**Fix**: `isTargetRoad()` now treats RoadID as authoritative whenever the field is present at all — a record's match is decided by `recordRoadId === roadId` alone in that case, with RoadName never consulted, never able to override or rescue a RoadID-level mismatch. RoadName-pattern matching is retained, unchanged, but demoted to fallback status: it is only ever consulted for a record with NO RoadID field at all (per the same inspection, no such record was observed among the real 706 — but the fallback is kept rather than removed, since a future TDX schema variation dropping RoadID for some records is not something this project can rule out from a static, point-in-time inspection). This is a general behavioral change to a shared function used identically by both the fixed-target admin probe/collage/publish-test endpoints AND the dynamic per-accident/per-shoulder-event pipeline — not a special case gated on road identity or KM value. Verified safe for 國1: grepped every test fixture in the repository for a record relying on the OR-fallback (a RoadID other than `'000010'` paired with a RoadName matching 國1's pattern) — none exists, so no legitimate existing 國1 test or known real-world 國1 record behavior changes.

### Part A — Dynamic Shoulder CCTV prepare-timeout

**The evidence.** 2026-08-21 afternoon, two real events:
- 國1 南向 87K+290～90K+900 (dynamic shoulder), system tick ~16:20: `cctvEligible:true` but `cctvSkippedByReason:'prepare-timeout'`, `imagePrepared:false`.
- 國3 南向 102K+100～103K+070, `UpdatedAt` ~15:49, system tick ~16:00: LINE text succeeded, Shared Feed persisted, no image at all — cause unknown going in, required independent diagnosis per the task's own instruction not to assume it matched case 1.

**Full trace performed**: `runLineBroadcast` → `resolveCctvEligibility` → `prepareCctvImageForEvent` (strategy dispatch) → `prepareSingleCctvImageForEvent` (per-event budget + cap) → `prepareSingleCctvImageWork` (metadata → candidate selection → `extractFirstJpegFrame` → `publishCollageImage`) → LINE push → Shared Feed. Every stage was read in full before any change was made.

**Case 1 root cause — NOT a blind timeout bump.** Per the task's own A1 instruction, the actual slow stage was identified before touching the budget number. This sandbox has no TDX/freeway.gov.tw network egress (and this round is explicitly forbidden from a real probe either way), so there is no way to directly re-measure real Production frame-fetch latency from here. What IS available, and is hard evidence already checked into this same codebase: `tdx/hsinchuCctvProbe.js` exports `FRAME_TIMEOUT_MS = 5000`, and uses it, unmodified, as the default timeout for exactly the same function (`extractFirstJpegFrame`) this single-CCTV path calls — via its own admin single-frame-probe endpoint (`handleHsinchuCctvFrame`), which IS exercised against real freeway.gov.tw URLs when an administrator invokes it manually. That 5000ms figure represents this codebase's own prior, separately-established judgment of "how long a single real frame fetch against this exact class of URL may reasonably take." `SINGLE_CCTV_PER_EVENT_BUDGET_MS` was 1500ms — less than a third of that already-accepted baseline, once the (cache-only, typically-fast) metadata read and (pure, synchronous) candidate selection are subtracted from what's left for the frame fetch itself. Metadata is a single memoized KV read (not the bottleneck architecturally — happens once per Cron run, near-instant against an in-memory-cached JSON blob), and R2 publish is a Cloudflare-internal write (not a public-internet hop, also not expected to dominate). The frame fetch — the one stage that leaves Cloudflare's own network and talks to freeway.gov.tw over the live public internet — is architecturally the only plausible dominant cost, and the codebase's own FRAME_TIMEOUT_MS baseline says as much directly.

**A2 — budget redesigned, all invariants preserved.** `SINGLE_CCTV_PER_EVENT_BUDGET_MS`: 1500ms → **6000ms** (covers a full FRAME_TIMEOUT_MS-class fetch plus margin for R2 publish/overhead). `MAX_SINGLE_CCTV_EVENTS_PER_RUN` stays **5** — this round changes how long one event's slot may take, never how many slots exist (lowering the cap was never asked for, and would only make MORE events skip CCTV, the opposite of what this fix is for). Every A2-required invariant was preserved by construction (only two numeric constants changed, none of the surrounding architecture V1.8.7.1 built): independent per-event budget (unchanged — still a fresh deadline anchored at that event's own turn); first-event-slow never starves 2nd/3rd (unchanged — no shared clock, verified again by the pre-existing `singleCctvBudgetFairness.test.js` suite passing unmodified); global safety cap (unchanged, same constant/value); no unlimited fetching (still a hard `budgetMs` ceiling via `withTimeout`); accident quad mechanism (byte-for-byte untouched — separate constant `CCTV_PREPARE_BUDGET_MS`, separate clock `cctvRunDeadlineAt`); single-event failure isolation (unchanged — still one `try/catch`+`withTimeout` per event); CCTV never blocks LINE text (unchanged); 0 extra TDX/PBS/Google calls (unchanged — still zero imports of `tdx/auth.js`/`tdx/client.js`); CCTV metadata cache-only (unchanged — `getFreewayCctvMetadata` untouched). Worst-case added wall-clock for one run's single-CCTV portion is now 5×6000ms=30s; Cloudflare Workers CPU-time metering (the dimension that's actually limited) is essentially unaffected, since virtually all of that time is spent awaiting network I/O, not executing JS.

**New instrumentation** (per A1's own suggested field list, adopted near-verbatim): `frameFetchDurationMs` (covers extractFirstJpegFrame's fetch+body-read as one combined measurement — deliberately not split further, since splitting it would require modifying that shared, already-ratified function used unchanged by the quad path too, which this round's own "不要為 dynamic shoulder 建第二套 CCTV pipeline" instruction argues against), `r2PublishDurationMs`, `timeoutStage` (`'metadata'|'candidate-selection'|'frame-fetch'|'r2-publish'`, captured via a small mutable `{stage}` tracker object shared into the async work function). All three are additive parameters on `buildTraceEntry`, following the exact pattern V1.8.7.0/.1 already established for `imageStrategy`/`cctvBudgetClass`/etc — never a schema rewrite. Whitelist discipline preserved: plain numbers/a short enum string only, verified by a dedicated privacy test asserting the serialized trace record never contains `VideoStreamURL`/`videoStreamUrl`/`freeway.gov.tw`.

**A real bug caught and fixed while building this instrumentation**: the first draft read `stageTracker.stage` EAGERLY, at the moment `withTimeout(work, budgetMs, {...timeoutStage: stageTracker.stage})` was called — which is synchronously right after `work` starts (still mid-metadata-await at that instant), so `timeoutStage` was permanently baked in as `'metadata'` regardless of where `work` actually was by the time it genuinely lost the race. Caught by a targeted test asserting the reported stage matched a deliberately slow frame fetch. Fixed by racing a unique `Symbol()` sentinel instead of a pre-built result object, and constructing `{reason:'prepare-timeout', timeoutStage: stageTracker.stage}` only AFTER the race resolves — so the stage is read live, at the actual moment of loss. This is a good illustration of why A3's own end-to-end test additionally asserts `timeoutStage` is merely one of the four known valid stages (not a hardcoded exact one) — the *exact* stage a live race lands on is legitimately timing-dependent in a way that must not make the test itself flaky, while the underlying mechanism (whichever stage it lands on is TRUE, not stale) is what actually matters and IS deterministically testable via the warm-metadata isolation technique in `test/cctvPrepareTimeoutStages.test.js`'s `A3` test.

**Case 2 (國3 102K+100) — independently diagnosed, confirmed NOT the same cause as case 1.** `cctv/dynamicCollage.js`'s `CCTV_SUPPORTED_ROADS` registry (see that module's own header comment, unchanged since V1.8.5) has only ever contained an entry for 國道一號 — deliberately: no Production-confirmed CCTV RoadID for 國道三號 has ever been observed from this codebase (TDX egress is blocked in this sandbox), and the module's own stated policy is to never guess one. `resolveRoadKey('國道三號')` correctly resolves to a valid road key (confirmed by reading `roadSectionLabel.js` — 國道三號 has real KM/section-label anchor data for OTHER purposes), but `CCTV_SUPPORTED_ROADS['國道三號']` is `undefined`, so `resolveCctvEligibility` structurally returns `{eligible:false, reason:'unsupported-road'}` before ever reaching metadata/candidate-selection/frame-fetch. This is exactly the fail-closed behavior the task's own A3 instruction asked for ("如果附近確實沒有可靠同方向 CCTV，保持 fail-closed，不要硬配遠距鏡頭") — correct, existing, by-design behavior, not a bug, and NOT a prepare-timeout. No code change was made for this case. Verified with a direct `resolveCctvEligibility(case2Event())` unit assertion plus a full-pipeline regression test confirming the LINE text still pushes and the Shared Feed product still persists, with the mocked `fetch` throwing on any `freeway.gov.tw` call (proving 0 frame-fetch attempts) and no CCTV metadata cache even seeded.

### Part B — Pipeline Trace filter failure

**The evidence.** Real Production mobile testing on `/admin/pipeline-trace-view`: selecting 來源=TDX國道 (`source=freeway`) AND 狀態=✅已播報 (`status=line-sent`) still returned entries with `source:'highway'`/`'pbs'` and `status:'event-ended'`/`'ineligible'` — the filter appeared not to work.

**Full trace performed**: HTML `<form>` (`pipelineTraceView.js#renderFilterForm`) → query string → `handlePipelineTraceView`'s `url.searchParams` parsing → `listPipelineTrace`'s KV read → filter predicates → `boundedLimit` → render. Two plausible hypotheses were tested and ruled out BEFORE the real cause was found (per the task's own "不要只修畫面" instruction — this was genuinely traced end to end, not patched at the first guess):
1. **AND-semantics bug** — ruled out. Code reading confirmed the filter predicates (`if (source && ...) continue; if (status && ...) continue;` etc, each independently gating) were already a strict AND, never an OR. A small isolated reproduction (4 mock records, one page) confirmed `source=freeway&status=line-sent` correctly returned only the one true match.
2. **`<select>` value / backend enum mismatch** — ruled out. `pipelineTraceView.js`'s `SOURCE_LABELS`/`STATUS_META` objects (the SAME objects the page already uses to render each row's own badges) were confirmed to match `computeStatus()`'s actual 12 possible return values, and the real `source` enum, 1:1 — no second, independently-maintained mapping exists, satisfying B2 directly. `<select>` submission itself was also confirmed to reflect live browser UI state on submit regardless of server-rendered `selected` attributes, ruling out a form-nesting/pre-selection bug.

**The real root cause — confirmed by direct reproduction, not just reasoning.** `listPipelineTrace`'s KEY-ENUMERATION loop (the cheap `kv.list()` pass that discovers which keys exist, strictly before any record body is fetched) exits with `if (page.list_complete || !page.cursor || keys.length >= MAX_ENTRIES_SCANNED) break;` — the `keys.length >= MAX_ENTRIES_SCANNED` (500) clause fires after just ONE `list()` page whenever Cloudflare's real page size (typically ≥500-1000 keys) already meets or exceeds 500, which is any day with more real trace volume than that. Given this module's own documented volume characteristics (every currently-Hsinchu-relevant event gets a fresh trace record on every ~10-minute Cron tick, not just new/changed ones — "low tens of events × every tick" by the module's own PERFORMANCE note, i.e. potentially thousands/day), this is a realistic, not edge-case, scenario. Since Pipeline Trace keys are constructed as `<prefix>:<date>:<epochMs>:<opaqueId>` (lexicographic order == chronological order, by design — see the function's own comment), stopping after page 1 permanently strands the scan on the OLDEST slice of the 24h window, never reaching the newest (most Production-relevant) entries via `cursor`. This explains BOTH observed symptoms at once: the unfiltered default view looked wrong (a stale, noise-heavy sample, not genuinely the newest events), and a filtered query could show zero matches — or wrong-looking noise — even when real matches existed, simply because they were never in the scanned set to begin with.

**Reproduced directly**: a paginated mock KV (real page-size + cursor semantics, unlike the pre-existing single-page mock in `test/pipelineTrace.test.js`) seeded with 1500 stale/non-matching records followed by 5 genuinely-matching recent ones, at a 1000-per-page size — confirmed the unfiltered view returned only stale records, and `source=freeway&status=line-sent` returned **zero** results despite 5 real matches existing, exactly matching the reported symptom.

**The fix.** Separated two previously-conflated concerns behind one constant:
- **New `MAX_LIST_PAGES = 40`** — bounds the KEY-ENUMERATION pass to a generous number of `list()` PAGE calls (high enough to comfortably reach the true end of a realistic 24h range), replacing the flawed `keys.length >= MAX_ENTRIES_SCANNED` break condition with a page counter (`pages >= MAX_LIST_PAGES`). The real termination condition stays `page.list_complete`/`!page.cursor` — this is only a defensive ceiling against a genuinely pathological key count (e.g. a future TTL/pruning bug), never the thing that decides "which keys are newest."
- **`MAX_ENTRIES_SCANNED = 500` — UNCHANGED.** This constant's actual job (how many of the now-CORRECTLY-identified newest keys get read+filtered, via `keys.slice(-MAX_ENTRIES_SCANNED).reverse()` and the second loop's `boundedLimit` check) was always correct; it just used to receive the wrong (stale) input. No change needed here — confirmed by the same reproduction test now passing with this constant untouched.
- **Filter-before-limit (B3 item 14) — confirmed ALREADY correct, no change needed.** The fetch+filter loop (`for (const key of newestFirstKeys) { if (records.length >= boundedLimit) break; ...apply every filter predicate...; records.push(record); }`) only ever counts a record toward `boundedLimit` AFTER it has passed every filter — this is genuinely "filter, then limit," never "grab N, then filter." Verified directly by a dedicated test: 1200 non-matching records surrounding exactly 1 real match, queried with `limit=5` — the real match is still found, proving a small limit cannot hide a real match that exists outside an arbitrary early slice.

**No Production decision logic touched** — `computeStatus`, classification, eligibility, dedupe, suppression, `broadcastHours`, CCTV eligibility, Shared Feed semantics, and LINE behavior are all completely unchanged; this fix is entirely inside the read-only admin observation path, per B4.

**View-layer addition (display-only)**: the HTML detail page now also renders `imageStrategy`/`selectedCamera`/`cctvBudgetClass`/`processingDurationMs`/`singleSlot` (a pre-existing V1.8.7.1 schema gap — these fields existed in `buildTraceEntry`/the JSON API but were never wired into the HTML view) alongside this round's own new `frameFetchDurationMs`/`r2PublishDurationMs`/`timeoutStage` — added together since both sets exist to answer the same "what happened to this event's CCTV attempt" question an administrator would naturally want visible on the same page.

**Tests**: 4 new in `test/pipelineTrace.test.js` — the paginated-KV reproduction (confirms the bug existed, then confirms the fix resolves it), filter-before-limit under real pagination, unfiltered-view-surfaces-true-newest, and the `MAX_LIST_PAGES` ceiling still bounding `list()` call count. All pre-existing `pipelineTrace.test.js`/`pipelineTraceView.test.js`/`pipelineTraceIntegration.test.js` tests (39 total, single-page mock) re-run and pass unmodified.

### Leading remaining explanation, and why it can't be fully fixed from here

The most likely remaining explanation is a **stale CLIENT-side view** — the admin's phone displaying a response body that was never actually re-fetched with the new query string (a cached page, a back-navigation to an earlier render, or a test performed against a URL visited before this round's or §33's fixes had fully propagated). This is a real, known class of mobile-browser behavior this project cannot fully rule out or directly fix: `pipelineTraceView.js` carries a hard architectural constraint (the existing strict Admin CSP, `default-src 'none'` with no `script-src` exception — see this file's own top comment, unchanged since V1.8.6.7) that means **zero client-side JavaScript is permitted on this page** — so there is no way to add a cache-bust query parameter, an `unload`-event-based bfcache opt-out, or any other JS-based anti-staleness mechanism here without a much larger, unauthorized architecture change this round was never asked to make and did not make.

### What was done instead — two concrete, in-scope improvements

Rather than stop at "found nothing, sorry," two genuinely useful, low-risk, fully in-scope (render-layer only) improvements were made:

1. **`renderActiveFiltersBanner`** — a new, always-present banner printed directly in the response body, stating in plain Traditional Chinese exactly which filter values the SERVER received and applied for THIS response (e.g. "✅ 目前套用篩選：來源=TDX 國道（freeway） 狀態=已播報（line-sent）", or "目前未套用任何篩選（顯示全部）" when none are active). This turns any FUTURE report of "the filter doesn't work" into an immediately, precisely diagnosable fact: if the banner shows the WRONG values, that's proof the query never reached the server correctly (a genuine, now-locatable bug); if the banner shows the RIGHT values but the rows below don't match, that's a genuine predicate bug (also now locatable, and distinct from the previous case); if the banner matches what was selected AND the rows are correct, but the admin's own screen still shows something different, that's conclusive evidence of a client-side staleness issue, resolved by a manual reload/cache-clear, not a code change. Built from the SAME `SOURCE_LABELS`/`STATUS_META` objects the rest of the page already uses — no second mapping introduced.
2. **Strengthened cache-prevention headers** — `Cache-Control: no-store, no-cache, must-revalidate, private` plus `Expires: 0`, set directly on this handler's own `Response`, on top of (not replacing) the existing `applyAdminSecurityHeaders` wrapper's `no-store, private` (index.js still applies that to every admin response uniformly). Belt-and-suspenders: even though `no-store` alone should already be sufficient per the HTTP cache spec, this is cheap, harmless, and directly targets the exact class of symptom (a stale served response) this round's leading hypothesis describes.
